## 一、为什么这件事必须服务端做

墨水屏终端是 ESP32-S3（240MHz、无中文字库、只有 480KB RAM）：

- **没有中文字库**：要显示中文得塞 GB2312 点阵字模（6763 字，几 MB Flash），排版还很丑
- **解 JPEG 极慢**：题目照片是 4032×3024、1.87MB，设备端解码一张要好几秒，还要再做抖动二值化

所以分工是：**服务端把一道错题排成一整页 800×480 的 1bpp 位图，设备只负责下载 48KB 和推屏**。设备端不排版、不解码、不显示中文，纯当"看图器"。

好处对你们也成立：排版规则改一行就能上线，不用每次重新烧固件。

## 二、需要新增的 3 个接口

### 1）队列

```
GET /api/eink/queue?limit=20
```

```json
{
  "count": 16,
  "updatedAt": "2026-11-17T10:00:00.000Z",
  "items": [
    {"id": 9,  "index": 1, "kp": "圆", "hasPhoto": false, "partCount": 1},
    {"id": 19, "index": 2, "kp": "圆", "hasPhoto": true,  "partCount": 2}
  ]
}
```

- 设备只用 `count`、`items[].id`、`hasPhoto`；其余字段可选
- **不要**把题目正文/附件塞进来，设备不需要（现有 `/api/review/queue` 的 14.7KB 全量 JSON 我们只是拿来验证连通性）
- 匿名可读，和现在一致，不要加鉴权（设备没有登录能力）

### 2）整页位图（核心）

```
GET /api/eink/page?id=19&mode=question    # 题目页
GET /api/eink/page?id=19&mode=answer      # 答案页
```

**硬性约束，任何一条不满足设备就显示异常：**

| 项 | 要求 |
|---|---|
| Body 长度 | **必须恰好 48000 字节**（800÷8×480），多一个字节都不行 |
| Content-Type | `application/octet-stream` |
| 排列 | 逐行，从左到右；每行 100 字节；共 480 行 |
| 位序 | **MSB 在左**（1 字节 = 8 个像素，最高位是这一行最左边的像素） |
| 颜色 | **0 = 黑，1 = 白**（不是反的，这个最容易搞错） |
| 压缩 | **不要 gzip**：设备不做解压（`Content-Encoding` 必须是空值） |
| 响应头 | `X-Etag: <内容哈希>`、`Content-Length: 48000` |
| 增量 | 设备会带 `If-None-Match`，命中同样内容就返回 **304 无 body** |
| 传输编码 | chunked 可以，设备能处理；但不能压缩 |

Python 里校验一句话就行：

```bash
curl -s "http://192.168.1.66:3000/api/eink/page?id=9&mode=question" | wc -c
# 期望输出：48000
```

### 3）预览图（给你们和排查用，设备不用）

```
GET /api/eink/preview?id=19&mode=question     → image/png
```

把同一份渲染结果存成 PNG 直接返回。这样后端改完排版，**用手机浏览器点开就能看到墨水屏上会长什么样**，不用每次烧板子验证。

## 三、排版要求（都是实测踩出来的，请照着做）

### 版面

| 区域 | 要求 |
|---|---|
| 页眉（y=10~56） | 左："错题 2/16"（26px 粗体）；右：知识点（24px 常规） |
| 分隔线 | y=64，2px |
| 正文（y=76~426） | x=24 起，宽 752（有图时让出右侧） |
| 页脚（y=436~480） | 按键提示 18px：`KEY1 < 上一题  KEY2 > 下一题  KEY3 答案` |
| 右下角 | **留空 60×24 的矩形**，设备要在这里画电量，不要放内容 |

### 字体

- 中文用 **思源黑体 / Noto Sans SC**（Windows 上可用 `msyh.ttc` 代替）
- 正文字号 **28px**，行高 1.55 倍；长题自动降字号 28→26→24→22→20，直到排得下
- **不要**低于 20px，墨水屏上会糊

### 有照片的题 —— 整页显示大图（关键决策）

一道作业页缩到 340px 后汉字只剩 2~3 个像素，等于看不清。实测结论：

- `mode=question` 且该题有 `attachments`：**整页 788×420 显示照片**，不排正文，页脚照常
- `mode=answer`：显示学生答案 / 错因 / 知识点文字
- 照片区确定性处理顺序（**这四步顺序错了就难看**）：
  1. **先 `exif_transpose` 旋转**（手机照片带 EXIF Orientation，不转会横躺）
  2. **按"白纸亮区"裁掉桌面和页边阴影**：缩到 120×90、亮度 ≥195 的像素求包围盒，裁到该范围（裁出的框小于 55% 就退回按"墨迹包围盒"裁）
  3. **边缘垫 6~10px 白**：否则局部均值窗口在边界会拉出一圈黑框
  4. **局部自适应阈值**：`BoxBlur(11)` 求局部均值，像素 < 均值减 8~12 判黑，其余判白
- **不要**用全局阈值、也不要对有文字的作业照片用 Bayer 抖动：实测原片灰度均值只有 143（偏暗），抖动出来是一团灰

如果附件里已有 `crop`（前端裁过图），优先用 `crop` 坐标，再走上面的 3、4。

### 无图的题

正文 28px 自动换行即可，实测 32 个汉字能排下，效果见预览图。

## 四、性能与行为约定

- 单页响应 < 300ms 最好；设备超时设了 10 秒
- 设备串行操作：拉队列 → 逐题拉页 → 翻页时直接推屏。**不会并发请求**
- 设备端会缓存上一页的 ETag，返回 304 时直接用缓存，所以 **ETag 必须随内容变化**（可用 `id + mode + updatedAt + revision` 做 md5）
- 题目更新（改答案、重新判错）后 ETag 要变，否则设备会一直显示旧页
